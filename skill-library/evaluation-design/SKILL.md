# 문제에 맞게 평가하기

먼저 사용자의 목표와 과제 유형을 확인한다. 목표를 수치화할 수 없는 부분은 사용자 흐름과 검증 사례로 남긴다. 외형상 그럴듯한 그래프를 만들기 위해 분류·학습 문제를 새로 만들지 않는다.

테스트 실행 선택·범위·시점은 하네스의 `skills/verify.md`를 따른다.

이 스킬은 평가 설계·지표·대안 비교를 맡는다. 데이터의 정제·조인·집계·검산 상세는 `skill-library/data-check/SKILL.md`를 따르고 같은 기록을 다시 만들지 않는다. 단순 분석에 평가 설계가 필요하지 않으면 data-check만 읽어도 된다.

## 지표 선택

먼저 하네스의 `skills/scope.md`에서 주된 목적과 산출물을 정한다. 계획형은 유효한 안과 대안 비교, 판단형은 기준별 판정과 근거, 분석형은 계산/주장의 재현과 출처를 평가한다. 아래 표의 기술적 지표는 실제로 해당 방법을 쓸 때만 선택한다. 품질·위험 판단이라는 이유만으로 분류 모델·ROC-AUC를 적용하지 않는다.

| 문제 | 필요한 근거 | 우선 비교 | 적절한 차트 |
|---|---|---|---|
| 이진 분류 | 평가 정답·연속 예측 점수, 양성 클래스 | 정밀도·재현율·선택 임계값의 오류 비용; 필요시 ROC-AUC/PR 지표 | ROC 또는 PR, 혼동행렬 |
| 수치 예측 | 같은 단위의 실제값·예측값 | MAE/RMSE 등 요구에 맞는 오차 | 실제값 대 예측값, 잔차 분포 |
| 검색·추천 | 질의별 관련성·정답 기준 | Recall@k/NDCG 등 사용 목적과 맞는 지표 | k에 따른 품질, 질의 그룹별 품질 |
| 제약 최적화 | 입력·필수 조건·계획 결과·독립 검사 | 제약 위반, 미처리, 목적값, 비용·불편·계산 시간 | 대안 간 절충, 조건 민감도, 탐색 진행 |
| 기준에 따른 판단 | 적용 기준/버전·관측값·판정·근거 위치 | 기준 적용 일치, 미확인/누락, 경계값·예외 처리; 참조 정답이 있을 때 판정 오류 | 판정 근거표, 조건별 분포·임계값 |
| 자료 분석·설명 | 원자료·출처/시점·계산/검색 경로·주장 | 계산 재현, 비교 기준 일치, 근거가 뒷받침하는 범위, 미확인·상충 | 비교표·추이·주장과 근거의 대응표 |
| 일반 앱 | 사용자 흐름·권한·실행 결과 | 필수 시나리오 통과, 오류·응답 시간 | 비교표, 조건별 지연 분포가 유용할 때만 |

Loss/목적함수는 알고리즘이 개선하려는 값, 평가 지표는 실제 성과를 확인하는 값이다. 같은 값일 수 있지만 자동으로 같다고 가정하지 않는다. AUC는 곡선 아래 면적이며, ROC-AUC는 정답과 점수가 있을 때 분류를 평가한다. 단일 클래스 평가셋에서 ROC-AUC를 계산하거나 미검증 상태를 0점으로 채우지 않는다. 불균형 분류는 유병률/양성 비율·임계값과 정밀도/재현율도 확인한다.

## 비교 절차

모든 과제에 개선안 두 개를 강제하지 않는다. 대안 비교가 목적이면 아래 절차를 쓰고, 판단/설명의 근거 확인이 목적이면 기준별 판정표나 주장별 근거표를 먼저 완성한다.

1. 핵심 지표·좋은 방향·단위·대상/기간·분모·성공 기준과 필수 제약을 정한다. 필요하면 하네스 기준 `templates/EVALUATION.md`를 실제 과제 문서에 통합한다.
2. 단순 기준안을 먼저 실행하고 개선안을 같은 평가 데이터와 제약에서 실행한다. 평가셋·전처리·지표 정의·실행 환경·랜덤 시드/반복 조건을 기록한다. 학습/검증/최종 평가를 분리하고 최종 평가로 반복 튜닝하지 않는다.
3. 최적화는 결정변수·필수 조건·선호 조건·목적 우선순위를 분리한다. 단위가 다른 지표를 근거 없는 가중치로 합치지 않는다. 제약 검사에 실패한 안은 목적값이 낮아도 유효한 개선안으로 채택하지 않는다. OR-Tools는 필요할 때 선택하는 라이브러리이며 필수 도구나 MCP가 아니다.
4. 같은 입력에서 기준안과 개선안의 차이를 표로 제시한다. 평균뿐 아니라 불리한 그룹·최댓값/분포·실행 시간도 필요에 따라 본다. 샘플 수·우연 변동을 고려하고 작은 차이를 일반적 우위로 단정하지 않는다.
5. 가장 중요한 차트 하나부터 만든다. 절충 그래프는 후보별 점, 수렴 곡선은 한 실행에서 기록한 실제 시간/반복과 최선의 유효한 목적값이다. 서로 다른 실행의 최종 점을 수렴 곡선처럼 연결하지 않는다. 가중치를 바꾼 목적값끼리 그대로 비교하지 않는다.
6. 조건 변경은 실제 재계산과 새 제약 충족을 검사한다. 조건이 바뀌어도 해가 같을 수 있다. 해 미발견/시간 초과와 불가능 증명을 구분한다. 일부 지표의 개선과 전체 사용자 경험의 개선을 구분한다.

계산 변경도 관련 수정을 묶어 고정 사례로 확인한 뒤 통합 시점에 필요한 전체 평가를 실행한다. 데이터·알고리즘·제약·지표 정의·설정·시드·의존성·실행 환경이 그대로라면 이전 측정 결과를 재사용할 수 있다. 차트의 제목·색·배치만 바꾸면 표시와 원본 값의 일치를 확인하고 최적화나 모델 평가 전체를 다시 돌리지 않는다. 값 집계·정규화·축 변환을 바꾸면 해당 계산을 재검증한다. 최종 평가셋은 반복 튜닝용으로 쓰지 않는다. 상세 기준은 하네스의 `skills/verify.md`를 따른다.

## 결과와 차트 만들기

실측 결과가 이미 집계돼 있다면 하네스의 `scripts/compare_runs.py`를 선택적으로 사용한다. Python 표준 라이브러리만 사용하며 입력을 외부로 보내지 않는다. 분류 예측으로 AUC를 계산하거나 원본 결과의 제약을 검증하는 도구는 아니다. 평가지표는 먼저 해당 작업 코드로 계산·검증한다.

이미 있는 결과 표·차트로 선택 이유를 설명할 수 있으면 도구용 CSV를 추가로 만들지 않는다. 핵심 산출물이 동작하고 비교할 실측값이 있으며 내보내기 비용이 남은 통합·설명 시간을 침범하지 않을 때만 사용한다. 도구를 쓰기 위해 제품의 저장 구조나 출력 계약을 바꾸지 않는다.

하네스 루트에서 형식 확인용 예제를 실행할 수 있다:

```sh
python3 scripts/compare_runs.py examples/runs.synthetic.csv --baseline base --metric cost:min --metric quality:max --output /tmp/evaluation-example.html
```

예제 숫자는 합성 자료이며 실제 성능 근거가 아니다. 실제 실행에서는 원본 CSV를 보존하고 과제 폴더의 새 출력 경로를 지정한다. 기존 출력은 명시적인 `--overwrite` 없이는 덮어쓰지 않는다.

CSV 필수 열: `run_id,data_version,constraint_set,metric_definition,method,evidence_kind,valid,runtime_seconds`와 지정할 지표 열. `evidence_kind`는 `measured` 또는 `synthetic`, `valid`는 `true` 또는 `false`다. 제약이 없는 평가도 동일한 평가 조건을 식별하는 값을 사용한다. 시드·하이퍼파라미터는 추가 열로 기록할 수 있다.

같은 파일의 데이터 버전·제약·지표 정의·근거 종류가 다르면 도구가 비교를 거부한다. 메타데이터가 같다는 것만으로 공정한 비교가 증명되지는 않으므로 실행 조건은 직접 확인한다. 지표가 두 개면 유효한 후보 사이의 관측된 파레토 후보를 표시한다. 이는 전역 최적성 증명이 아니다. 시간은 표에서 별도로 확인하며 두 지표의 파레토 계산에는 포함하지 않는다.

최종 설명은 ‘선택한 안 → 기준안 대비 변화 → 받아들인 손해 → 검증 범위 → 없는 데이터로 확인 못한 것’ 순서로 남긴다. 정답이 없으면 정확도를 주장하지 않고, 합성 입력의 동작 확인을 실제 분포의 성능 검증으로 바꾸지 않는다.
