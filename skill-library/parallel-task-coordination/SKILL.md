# 필요한 작업만 나누기

제공 기능·허용 모델·권한을 먼저 확인한다. 별도 실행기·MCP·역할 설정은 설치하지 않는다. 이 문서는 작업 조율 절차이며 실행 기능을 추가하지 않는다.

테스트 실행 선택·범위·시점과 병렬 작업의 검사 담당 기준은 하네스의 `skills/verify.md`를 따른다.

## 실행 방식 선택
- **서브에이전트:** 메인이 위임·상태 확인·결과 회수를 할 수 있고 작업 범위가 분명할 때 사용한다.
- **별도 터미널의 독립 세션:** 환경이 허용하고 사용자가 두 작업에 직접 지시·실행·확인을 이어갈 필요가 있을 때 선택할 수 있다. 사용자가 세션을 열고 공통 계약을 전달한다. 세션 간 대화·상태·모델·지침이 자동 공유된다고 가정하지 않는다.
- **순차 작업:** 선행 결과에 의존하거나 파일·자원이 겹치고 조율 비용이 큰 경우 사용한다. 서브에이전트 미지원만으로 별도 세션까지 불가능하다고 단정하지 않는다.

터미널이 둘이어도 파일 시스템·DB·캐시·프로세스가 격리된 것은 아니다. 메인과 다른 세션의 작업 경로가 같은지 확인한다. 역할은 실행 방식과 별개다.

주된 목적에 맞춰 메인은 최종 산출물·입출력 계약·통합을 맡고, 독립 작업자는 계획 계산 / 기준별 판정 규칙·근거 정리 / 자료 처리·계산·검색 중 필요한 부분을 맡는다. 보고서 과제에서는 화면 대신 표·차트·설명 파일로 통합한다. 반환 형식은 하네스의 `skills/scope.md`에서 선택한 산출물에 맞춘다.

| 역할 | 맡길 일 | 수정 권한 |
|---|---|---|
| 메인 | 요구 확정·핵심 구현·통합·최종 검증 | 공용 설정·공유 타입·잠금 파일 포함 |
| 조사 담당 | 기존 코드에서 특정 질문의 답과 근거 찾기 | 읽기 전용 |
| 검증 담당 | 독립된 요구사항·예외 검토와 테스트 | 기본 읽기 전용, 테스트 실행 시 공유 자원 충돌 확인 |
| 구현 담당(필요시) | 인터페이스가 정해진 독립 기능 | 지정한 파일만 |

1. 메인이 진행할 일과 독립적인 작업만 맡긴다. 짧은 작업이나 결과를 기다려야 다음 단계가 가능한 일은 직접 한다.
2. 서브에이전트는 첫 읽기 작업 하나로 실제 생성 ID와 결과를 확인한다. 별도 세션은 담당 역할과 실제 작업 폴더를 각각 확인한다. 처음에는 작업자 1명으로 시작하고 필요할 때만 늘린다. 권장 상한은 메인 외 2명이며 환경 한도가 우선이다. 중첩 위임은 하지 않는다.
3. 지시에는 **목표 / 작업 루트·입력 / 허용 수정 파일 / 완료 조건 / 테스트 선택·범위·시점 / 예상 종료 시각 / 반환 형식**을 넣는다. 예: “읽기 전용으로 입력 검증 누락 3개를 찾아 파일·위치·재현 입력으로 반환. 테스트 실행은 선택 대기. 5분 안에 확인한 범위까지만 보고. 추가 위임 금지.”
4. 같은 파일·DB·캐시·서버 포트를 동시에 바꾸지 않는다. 격리가 확인되지 않으면 순차 수행한다. 메인은 맡긴 일을 중복 구현하지 않는다.
5. 실행 ID·상태·실제 시각을 확인하고 아래 ‘지연·실패와 안전한 인수’를 따른다. 요청한 종료 시각은 강제 timeout이 아니다.
6. 결과는 결론·근거 파일·변경 범위·실제 실행 명령/결과·미해결 사항으로 받는다. 테스트 방침·승인된 범위·미실행 항목도 다음 세션에 전달한다.
7. 통합·검증·제출 시간을 남긴다. 120분 이후 새 기능 위임은 멈춘다. 제출 시 미완료 작업이 파일을 바꾸지 않도록 정리하되 앱 서버·감독 프로세스는 유지한다.
8. 실제 AI 금지 후속 평가에서는 사용하지 않는다.

## 앱 작업의 소유권 예시

시작 전에 실제 경로를 정해 아래 계약을 양쪽에 전달한다. 예시 경로는 그대로 만들 의무가 없다.

| 담당 | 수정 범위 예시 | 완료 근거 |
|---|---|---|
| 메인·통합 담당 | UI·API·저장·권한·공유 타입·공용 설정·공통 기록 | 기준안부터 실제 흐름 연결, 최종 통합 |
| 독립 구현 담당 | 계약이 정해진 계산/판정/분석 모듈·그 테스트·별도 결과 폴더 | 입력·출력, 구현과 검사 근거, 미해결 사항 |

이미 ‘프론트 구현 / 알고리즘 테스트’로 나눴다면 위 예시로 재배치할 필요는 없다. 프론트 세션은 UI, 테스트 세션은 테스트·입력·별도 결과만 수정하고 알고리즘 본체는 지정 소유자 한 명이 수정한다. 둘 중 통합 담당을 정한다. 실제 소유 범위는 `docs/DECISIONS.md`의 ‘진행·핸드오프’(또는 정한 공식 기록)에 한 번 기록하며 다른 문서에 별도 역할표를 만들지 않는다.

- 공통 계약: 입출력 필드·타입·단위·정렬/동점 기준·빈 결과·오류 형식 중 해당 항목, 소유 파일, 테스트 대상 상태, 포트/출력 경로, 결과 전달 위치를 정한다.
- 계약 변경은 상대 세션에 전달하고 확인한 뒤 적용한다. 알고리즘 본체 수정이 필요하면 소유 담당에게 전달하거나 작업을 멈추고 명시적으로 소유권을 넘긴다.
- 고정한 입력·대상 코드로 테스트한다. 테스트 중 관련 코드·입력·설정·의존성·환경이 바뀌면 결과가 어느 상태를 검증했는지 표시하고 묶음 종료 후 영향받은 검사를 다시 실행한다. 무관한 UI 문구나 문서 변경만으로 알고리즘 검사를 반복하지 않는다. 커밋 식별자가 없으면 관련 파일 스냅샷/해시 등으로 구분할 수 있다.
- 각 세션은 자기 결과만 별도 기록하고 통합 담당이 공통 문서에 합친다. 같은 로그나 문서를 동시에 덮어쓰지 않는다. 별도 세션에서는 사용자가 결과 경로와 계약 변경을 전달해야 할 수 있다.
- 양쪽 작업 완료 후 수정 중인 작업이 없는지 확인하고, 모의 응답을 실제 알고리즘으로 연결해 핵심 흐름과 예외를 다시 검증한다. 분리된 테스트의 통과만으로 통합 완료라고 하지 않는다.
- 전체 검증 중에는 대상 파일·공유 자원을 고정한다. 실패 수정은 관련 사례부터 재검증하고 영향이 넓거나 불명확할 때 범위를 넓힌다. 다음 세션에는 완료한 변경 묶음·재사용 가능한 근거·검증 대기 항목과 담당만 전달한다. 상세 기준은 하네스의 `skills/verify.md`를 따른다.

## 지연·실패와 안전한 인수

1. 종료 목표를 넘기거나 막혔다면 현재 완료 범위·수정 중 파일·남은 일·예상 종료를 받는다. 우선 범위를 줄이거나 이미 확보한 기준안을 사용한다. 메인은 자기 소유의 독립 작업만 계속하며 지연된 작업을 중복 구현하지 않는다.
2. 인수가 필요하면 기존 작업자에게 쓰기·관련 백그라운드 작업 중단과 변경 내역 반환을 요청한다. **중단 요청·무응답·도구 시간 초과는 중단 확인이 아니다.** 실제 종료/유휴 응답과 쓰기 작업 종료를 확인한 뒤 소유권을 넘긴다. 별도 터미널은 사용자에게 해당 세션의 중단 확인을 전달받는다. 앱 서버·감독 프로세스는 종료하지 않는다.
3. 중단이 확인되면 현재 차이와 부분 결과를 읽고 인수자·파일·계약 버전·시각을 기록한 뒤 한 명만 이어서 수정한다. 무작정 되돌리거나 다른 작업자의 변경을 삭제하지 않는다. 필요한 재검증은 `skills/verify.md`의 정책을 따른다.
4. 중단을 확인할 수 없으면 해당 파일을 재배정하지 않는다. 격리된 결과는 통합을 보류하고 기존의 안정된 기준안을 유지한다. 같은 작업 폴더라면 ‘통합 안 함’만으로 수정이 사라지지 않으므로 영향받은 흐름의 실행·완료 판정을 보류한다. 지연 시 재사용할 기준안·복사본이 필요하면 위임 전에 허용된 범위에서 준비한다. 미완료 상태와 영향을 사용자에게 알린다.
