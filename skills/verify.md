# verify — 실행해서 확인하고 기록하기

목표: 변경 묶음별로 테스트 실행 여부를 사용자에게 확인하고 선택한 범위만 실행한다. 과제 경과 120~150분에는 통합 검증과 핵심 결함 수정 시간을 확보한다. 공식 기록 양식이 있으면 사용하고, 없으면 선택적으로 `templates/VERIFY.md`를 참고한다.

## 변경 후 테스트 선택

- 수정 묶음이 끝나면 실행 전에 **변경 요약 / 권장 검사·범위 / 예상 시간 / 생략 시 미확인 항목**을 짧게 알리고 선택을 묻는다. 예상 시간은 이전 실행 등 근거가 있을 때만 제시하고 없으면 ‘미상’이라고 한다. 질문 도구가 있으면 선택지를 제공하고, 없으면 번호로 답할 수 있는 질문을 한다.
- 선택지는 **① 지금 관련 테스트 실행 ② 통합 시점에 실행 ③ 이번 변경의 테스트 생략**이다. 권장안을 표시할 수 있지만 선택된 기본값·무응답·시간 경과를 동의로 취급하지 않는다. 응답 전에는 선택 대상 테스트를 실행하지 않고 독립적인 구현·문서 정리만 계속한다.
- 기본 적용 범위는 현재 변경 묶음이다. 사용자가 이미 해당 범위를 테스트하라고 했거나 ‘이 작업은 자동 테스트’, ‘통합할 때만 테스트’ 등 방침을 정했다면 그대로 따르고 중복 질문하지 않는다. 선택된 검사에 필요한 같은 범위의 실패 수정·재검증도 포함하되, 범위나 예상 비용이 크게 늘면 다시 묻는다. 이후 독립적인 변경 묶음에는 새 선택을 받는다.
- ‘통합 시 실행’은 해당 범위의 검사를 대기 목록에 남기고 통합 때 실행하는 선택이다. 같은 범위는 다시 묻지 않는다. ‘생략’은 해당 범위를 미실행으로 기록한다. 실행되지 않은 검사를 통과로 쓰지 않는다.
- 자동 테스트·검증용 빌드·브라우저 시나리오·벤치마크에 적용한다. 코드/차이 읽기와 변경 내용 설명은 실행 테스트와 구분한다. 필수 프로젝트/CI 검사라면 실제 요구 문서·명령을 밝혀 안내하고, 생략 가능한 선택 검사와 구분한다. 이 하네스의 권장 검사를 임의로 필수라고 하지 않는다.
- 권한·데이터 쓰기·공유 계약 변경은 의존 작업 전에 관련 검사를 권장한다. 실행 여부는 위 선택을 따른다. 미실행이면 영향과 남은 확인을 알리고 검증 완료로 가정하지 않는다.
- 병렬 작업에서는 메인이 검사 목록을 모아 한 번 질문하고 선택 범위·시점을 작업자에게 전달한다. 작업자는 선택 범위를 벗어난 테스트를 자동으로 추가하지 않는다.

질문 예시: “필터와 빈 결과 처리를 수정했습니다. 관련 정상·경계 사례를 확인하는 것을 권장합니다. 예상 시간은 미상이며, 생략하면 빈 결과 처리가 미검증으로 남습니다. ① 지금 실행 ② 통합 때 실행 ③ 이번 변경은 생략 중 선택해 주세요.”

## 수정과 검증의 간격

1. 수정 전에 관련 변경을 하나의 묶음으로 정한다. 예: 같은 화면의 라벨·간격·오류 표시, 같은 계산 경로의 필터·경계 조건. 묶음의 완료 조건과 확인 방법만 짧게 정하고 중간 편집마다 전체 검사하지 않는다. 묶음이 너무 커지면 기능별로 나누며, 10~15분 정도를 시작 기준으로 조정한다.
2. 묶음이 끝나면 위 선택을 받고 실행하기로 한 범위만 확인한다. 정상 사례와 바꾼 경계 조건의 결과를 기록한다. 필수 프로젝트/CI 검사는 유지한다.
3. 권한·데이터 쓰기·DB 스키마·공유 API 계약 변경의 검사는 의존 작업 전에 제안한다. 빌드 불능이나 데이터 손상 위험이 보이면 즉시 알리고 그 상태에 의존하는 작업을 멈춘다. 이때도 선택하지 않은 테스트나 무관한 전체 검사를 자동 실행하지 않는다.
4. 첫 핵심 흐름이 연결될 때 짧은 통합 실행을, 제출 전에는 안정된 상태의 전체 검증을 제안하고 선택/기존 방침을 따른다. 이후 수정은 영향받은 검사와 회귀 사례를 우선하며 공통 설정·의존성·스키마가 넓게 바뀌거나 영향이 불명확하면 확대 범위를 제안한다. 실패나 변경에 따른 필요한 재검증 횟수를 ‘무조건 한 번’으로 제한하지 않는다.
5. 이미 통과한 검사는 관련 코드·입력 데이터·설정·의존성·실행 환경이 그대로면 근거를 재사용한다. 새 커밋이나 답변을 쓴다는 이유만으로 반복하지 않는다. 이전 실행 시점/대상과 재사용 이유를 남기고 방금 실행했다고 쓰지 않는다. 영향이 불명확하면 필요한 재검증 범위를 제안한다.

| 변경 묶음 | 우선 확인 | 검증 범위를 넓히는 때 |
|---|---|---|
| 문구·간격·색상 | 해당 화면의 잘림·대비·조작; 문서는 링크·일관성 | 공용 스타일/컴포넌트 등 영향이 넓어졌을 때 관련 화면으로 확대 |
| 알고리즘·집계·목적함수 | 고정 입력의 정상·경계 사례, 제약 검사, 기준안 비교 | 최종 통합 또는 결과를 소비하는 경로까지 영향이 퍼질 때 |
| API·권한·저장 | 변경 계약·접근 제어·저장/조회 경로를 조기에 확인 | 공통 계약/데이터 구조가 여러 흐름에 영향을 줄 때 |
| 공유 의존성·빌드 설정 | 빌드와 영향받는 검사 | 영향 범위가 넓거나 불명확할 때 |

병렬 작업자는 선택된 자기 변경 묶음의 검사만 맡고, 통합 담당 한 명이 선택된 전체 검증을 실행한다. 통합 시 검증 대상 파일을 동시에 수정하지 않는다. 기다리는 검증은 기존 작업 기록에 한 줄로 남기며 별도 관리 도구는 만들지 않는다.

## 순서

아래는 실행하기로 선택한 범위에 적용하는 절차다. 미루거나 생략한 항목은 실행하지 않고 미실행으로 기록한다.

1. **자동 테스트.** 위 기준으로 필요한 기존 검사를 선택해 실행하고 명령·결과·출력 위치를 남긴다. 테스트가 없다면 핵심 계산·권한·반복 재현이 필요한 결함에 한해 작은 테스트를 추가한다. 단순 문구·배치 변경마다 새 테스트를 만들지 않는다. 테스트가 안 돌면 "안 돈다"고 적는다.
2. **제공 환경의 Browser에서 직접.** 웹 서비스라면 서버를 `0.0.0.0`에 바인딩하고 실제 포트·경로를 맞춘다. 서버 터미널을 유지한다. 웹 과제가 아니면 해당 실행·출력 경로로 검증한다. 확정한 핵심 사용자 흐름을 처음부터 끝까지 내 손으로 실행한다. 단계마다 기대와 실제를 적는다.
3. **요구사항 대조.** 담당자 답 하나하나에 O/△/X를 매기고 근거를 적는다. X는 숨기지 않고 README의 "뺀 범위"나 "한계"로 보낸다.
4. **예외 재현.** 과제에 맞는 위험한 사례 몇 개를 고른다. 예: 빈 값·형식 오류·중복 실행·저장 후 다시 열기·실패 후 재시도. 입력/조작 → 기대 → 실제 → 영향으로 기록하고, 수정 묶음이 끝나면 해당 사례와 영향받은 정상 흐름을 다시 실행한다. 데이터·AI 출력 과제는 해당 보조 스킬의 검산·평가 기준도 사용한다.

## 검증의 범위
- 필요한 필드·정답 라벨·드문 사례·기간·규모가 입력 데이터에 있는지 확인한다. 없으면 검증하지 못한 주장과 필요한 추가 자료를 명시한다.
- 합성/모의 입력은 명시적으로 표시하고 분기 동작 확인에 쓴다. 실제 분포·정확도·운영 성능을 입증했다고 쓰지 않는다. 정답이 없으면 정확도 대신 확인 가능한 일관성·형식 등을 기록한다.
- 환경/시간 제약, 설계상 받아들인 단점, 재현한 결함, 증거가 없어 미검증인 항목을 구분한다. 각각 영향·현재 대응·다음 확인을 남긴다.
- 프론트·알고리즘을 나눠 작업했다면 같은 최종 코드에서 실제 입출력 계약을 통과하는 흐름을 실행한다. 모의 응답으로 확인한 UI와 실제 알고리즘을 연결한 검증을 구분한다.

## 규칙
- AI가 "테스트 통과했습니다"라고 하면 명령과 출력을 보여 달라고 한다. 출력 없이는 기록하지 않는다.
- 여기서 발견한 버그는 핵심 요구·계산 정확성·권한·데이터 보존·실행을 해치는 것부터 고친다. 나머지는 한계로 적는다. 2:00 (120분) 이후 새 기능은 없다. 수정 묶음에 영향받은 경로를 다시 검증한다. 2:30 (150분)에 문서 정리로 전환하고 못 끝낸 검증은 미실행으로 기록한다.
- 고친 내용과 이유는 작업 기록에 한 줄 남긴다.

## 산출물
- 테스트·사용자 흐름·요구사항 대조·예외 검토 결과를 기록한다. 하지 않은 검증은 이유를 적는다. 별도 문서가 필수는 아니다.
