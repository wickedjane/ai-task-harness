# scope — 범위와 설계 결정

목표: 경과 15~30분에 핵심 흐름·성공 기준·제외 범위를 정한다.

1. 공식 README·기존 코드·확인한 요구사항을 바탕으로 아래 세 유형 중 주된 목적과 첫 산출물을 정한다. 유형에 억지로 맞추지 말고 필요한 흐름·데이터·전달 형식을 선택한다.
2. AI와 대안을 비교하고 최종 선택 이유·포기한 범위를 기록한다. 이미 제공된 스택·구조를 우선 활용한다.
3. 구현 예산 90분을 기준으로 위험 지점 두세 개와 검증 방법을 정한다.
4. 서버·저장소·권한은 실제 요구와 실행 환경에 맞춰 선택한다. 필요한 입력 검증·보안·오류 처리를 과설계라는 이유로 빼지 않는다.
5. 지금 쓰지 않는 추상화·기능·의존성은 줄인다. 파일 수나 특정 프레임워크를 일률적으로 제한하지 않는다.

산출물은 핵심 흐름·성공 기준·제외 범위와 주요 결정이다. 공식 문서 양식이 있으면 거기에 통합한다.

## 목적에 따라 흐름과 결과를 고르기

| 주된 목적 | 작업 흐름 | 최소 산출물 | 완료를 판단할 근거 |
|---|---|---|---|
| 계획 생성 | 수요·자원·설정 확인 → 필수/선호 조건 분리 → 기준안 생성 → 개선안 비교 → 선택/확정 | 실제 계획·배정표, 적용 조건/입력 버전, 미처리·위반 사유, 기준안 비교 | 결과가 필수 조건을 지키는지, 누락·중복 여부, 동일 조건의 비용·품질 차이 |
| 품질·위험 판단 | 대상·근거 수집 → 판정 기준/버전 확인 → 항목별 판정 → 근거·미확인 표시 → 검토/다음 조치 | 기준별 적합·부적합·미확인 표, 관측값·근거 위치, 보류/추가 확인 사유 | 기준 적용의 일관성, 경계값 처리, 근거 누락을 합격으로 처리하지 않는지 |
| 자료 분석·설명 | 질문·독자 정하기 → 자료/범위 확인 → 비교 기준 정리 → 계산/검색 → 결론과 근거 연결 → 한계 설명 | 표·차트 또는 답변/보고서, 주장별 출처·계산 근거, 가정·미확인 사항 | 계산 재현, 출처가 주장을 뒷받침하는지, 사실과 추정·인과 해석의 구분 |

혼합 과제는 주된 흐름 하나에 필요한 보조 단계를 붙인다. 예를 들어 판정 결과를 계획의 입력으로 쓰면 미확인/부적합 대상을 어떻게 처리할지 계약에 명시한다. 세 유형의 앱을 각각 만들지 않는다. 예측 모델·최적화 라이브러리·LLM은 목적과 데이터에 맞을 때 선택한다.

### 계획 생성

- 어떤 값을 결정하는지, 반드시 지켜야 할 조건과 개선할 지표·우선순위를 정한다. 필수 위반을 좋은 평균 점수로 상쇄하지 않는다.
- 단순 기준안부터 전체 흐름을 연결한다. 계산 결과는 유효한 안/부분안/시간 내 미발견/입력 오류 등을 구분하며, 해가 없다는 증명과 탐색 실패를 혼동하지 않는다.
- 같은 입력·제약에서 기준안과 개선안을 비교한다. 설정 변경이 계산에 전달됐는지와 새 조건을 만족하는지를 확인하며, 결과가 반드시 달라져야 한다고 가정하지 않는다.

### 품질·위험 판단

- 기준의 출처·적용 범위·버전·임계값과 예외를 확인한다. 과제에 없는 기준이나 가중치를 임의로 승인 규칙으로 만들지 않는다.
- 기준별로 관측값·적합/부적합/미확인·근거 위치를 연결한다. 결측·상충·부족한 표본은 별도 표시한다. 필수 미충족이나 미확인을 총점에 묻지 않는다.
- 자동 판정과 사람이 결정할 범위를 정한다. 우선순위 점수와 최종 승인 상태를 구분하고, 추가로 필요한 근거와 다음 조치를 제시한다.

### 자료 분석·설명

- 질문·대상 독자·기간·자료 버전을 정하고 단위·분모·비교 범위를 맞춘다. 수치 분석은 계산 경로, 문서 설명은 인용 위치로 근거를 연결한다.
- 자료가 충돌하거나 부족하면 확인 가능한 범위까지만 답한다. 관측된 차이와 원인 추정, 사실과 시나리오를 구분한다.
- 재현 가능한 계산/검색과 근거 연결을 먼저 완성한다. 보고서면 파일로 전달하고 탐색·상호작용이 요구될 때 화면을 만든다.

## 화면·저장·계약

화면이 필요하면 계획형은 설정→계획/비교→확정, 판단형은 대상 목록→기준/증거→검토 결과, 분석형은 질문/필터→표·설명→출처 확인을 우선한다. 실제 권한과 저장 필요에 따라 줄인다.

계약에는 공통으로 입력/설정 버전과 처리 상태를 두고, 계획형은 계획·미처리·지표, 판단형은 기준 버전·항목별 판정·근거·추가 확인, 분석형은 주장·출처/계산·범위·한계 중 필요한 필드를 정한다. 하나의 거대한 공통 스키마를 강제하지 않는다. 유형별 상세 기록이 필요하면 기존 REQUIREMENTS·EVALUATION 양식의 해당 칸만 사용한다.

입력·권한·업무 제약·판정 규칙은 제품 동작의 일부다. 개발 후 테스트 실행 여부는 `skills/verify.md`의 사용자 선택을 따른다. 테스트를 생략했다고 제품의 필수 규칙을 끄거나 결과를 검증 완료로 표시하지 않는다.

필수 요구마다 입력/동작 → 기대 결과 → 확인 방법을 연결한다. UI가 필요한 과제에만 정상·로딩·빈 데이터·오류·재시도 상태를 설계한다. 데이터 분석이나 보고서 과제라면 핵심 흐름을 입력 → 변환/분석 → 결과 검산으로 잡고 불필요한 화면·서버를 추가하지 않는다.

설계 시 구성요소별 책임·입출력 계약·상태 저장 위치·실패 처리를 실제 파일/함수에 연결한다. 대표 입력 하나의 흐름을 도식이나 몇 줄로 설명한다. 중요한 선택은 실제 대안·판단 기준·얻는 점·받아들인 단점·포기한 범위·재선택 조건을 비교한다. 필요하면 `templates/DECISIONS.md`에 기록하고 설계 변경 때 갱신한다.
핵심 설계가 정해지면 `skills/explain.md`의 중간 이해 점검을 시작한다. 전체 이해를 제출 직전에 처음 확인하지 않는다.
