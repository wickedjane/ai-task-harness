# explain — 제출 전에 이해도를 점검하기

목표: 구현 중 결정 이유를 기록하고 제출 전 점검을 마친다. 기본 권장 배분은 경과 160~170분의 10분이며, 이후 10분은 제출 절차에 쓴다. 공식 마감이 더 이르면 배분을 줄인다.
이 절차의 AI 도움은 허용된 과제 수행 또는 연습 단계에서만 사용한다. 실제 후속 서술형에서는 AI를 사용하지 않는다.

## 구현 중 이해 점검
핵심 설계 결정·기능 완성·중요한 알고리즘 변경 때마다 짧게 진행한다. 권장 1~2분이며 기존 구현 시간 안에 포함한다. 사소한 수정마다 작업을 멈추지 않는다.

1. AI가 현재 구현의 구성요소·책임과 대표 입력 → 처리 → 상태/저장 → 출력 경로를 실제 파일/함수로 설명한다. 선택 이유·대안·받아들인 단점과 검증 근거를 함께 짚는다.
2. 사용자가 핵심 흐름이나 선택 이유를 자기 말로 짧게 설명해 본다. AI는 실제 코드와 다른 부분만 교정한다. 답을 들었다는 이유로 이해했다고 기록하지 않는다.
3. 사용자가 직접 확인할 입력·조작·손계산 사례 하나를 제시한다. 결과를 듣기 전에는 사용자 검증 완료로 쓰지 않는다. AI의 확인과 사용자의 판단을 구분한다.
4. 중요한 내용만 기존 작업 문서에 남긴다. 공식 양식이 없으면 `templates/DECISIONS.md`와 `templates/VERIFY.md`의 필요한 항목을 실제 과제 폴더에서 사용한다. 문서를 에디터로 열어 설명을 읽을 수 있게 경로를 알려준다.

## 제출 전 점검
1. 주요 파일 역할과 데이터 흐름을 내 말로 설명한다. 불명확한 부분은 제공된 AI에게 설명을 요청하고 실제 코드와 대조한다.
2. 주요 결정·검증 결과·미검증·한계를 기록과 맞춰 본다. 아래는 연습용 질문이며 실제 문항을 예측하거나 보장하지 않는다.
   - 구조를 선택한 이유와 포기한 대안은 무엇인가?
   - 입력이 어떤 함수·파일·저장소를 거쳐 결과로 나오는가?
   - 어떤 명령과 조작으로 동작을 확인했는가?
   - 실패하는 입력과 아직 검증하지 못한 상황은 무엇인가?
   - 시스템의 구성요소는 어떤 책임을 가지며 어떤 계약으로 연결되는가?
   - 선택한 안의 이점·단점과 포기한 것은 무엇이며 어떤 조건이면 대안을 택할 것인가?
   - 데이터에 어떤 필드·정답·사례가 없어 무엇을 검증하지 못했는가? 대체 확인으로 어디까지 말할 수 있는가?
   - 환경/시간 제약·설계상 절충·알려진 결함·미검증을 구분할 수 있는가?
   - 병렬 작업은 어떻게 나눴고 최종 결합이 정상임을 어떻게 확인했는가?
   - 시간이 더 있다면 무엇을 먼저 고칠 것인가?
   - AI 제안을 어떻게 채택·수정·거절했고 내가 검증한 부분은 무엇인가?
3. 제출 직전에 구조를 크게 바꾸지 않는다. 사실과 불확실성을 구분하고 제출 확인으로 전환한다.

## 직접 답변 연습
- 한 문제당 5분으로 연습한다. 먼저 스스로 타이핑하고, 연습이 끝난 뒤에만 AI 피드백이나 코드 대조를 한다.
- 권장 연습 배분: 30초 질문 이해 → 3분 30초 직접 작성 → 1분 사실·누락 점검. 공식 세부 배분이 아니다.
- 결론 → 이유 → 구체적인 구현·검증 근거 → 한계 순으로 답한다. 외운 일반론보다 자신의 수행 사실을 설명한다.
- 질문 전제가 실제 구현과 다르면 그 차이를 먼저 밝힌다. 미구현·미검증을 완료했다고 말하지 않는다.
- 실제 후속 서술형은 AI와 복사·붙여넣기를 사용하지 않는다. 제출된 답안으로 되돌아갈 수 없고, 다음 문항 타이머는 직전 답안 제출 즉시 시작되며 시간이 끝나면 현재 답안이 확정된다.
