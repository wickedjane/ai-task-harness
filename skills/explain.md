# explain — 구현을 설명하고 제출 전 요약하기

목표: AI가 구현·선택 이유·검증·한계를 짧게 설명하고 사용자가 제출 전에 훑을 요약을 만든다. 경과 150~170분에는 AI가 산출물 문서와 SUMMARY를 정리하고 사용자는 요약을 읽는다. 직접 작성·재진술·답변 연습은 요구하지 않는다. 이후 10분은 제출 절차에 쓰며 공식 마감이 더 이르면 배분을 줄인다.
이 절차의 AI 도움은 허용된 과제 수행 또는 연습 단계에서만 사용한다. 후속 평가에서는 파일을 열람하지 못한다고 전제한다. 실제 후속 서술형 중에는 AI를 사용하지 않으며 준비 문서를 볼 수 있다고 의존하지 않는다.

## 구현 중 설명과 요약
핵심 설계 결정·기능 완성·중요한 알고리즘 변경 때 짧게 설명한다. 사소한 수정마다 작업을 멈추거나 사용자의 요약 답변을 기다리지 않는다.

1. AI가 현재 구현의 구성요소·책임과 대표 입력 → 처리 → 상태/저장 → 출력 경로를 실제 파일/함수로 설명한다. 선택 이유·대안·받아들인 단점과 검증 근거를 함께 짚는다.
2. AI가 `templates/SUMMARY.md`를 실제 작업 폴더의 `docs/SUMMARY.md`로 사용해 해당 항목을 2~3문장으로 작성·갱신한다. 기존 사용자 메모는 보존한다. 구현·결정 기록·실행 근거를 대조하고 없는 근거는 미확인으로 표시한다. AI가 대신 사용자 경험을 꾸미거나 설명만으로 이해 완료를 기록하지 않는다.
3. 사용자 직접 확인과 AI 실행·코드 검토·미실행을 구분한다. 사용자에게 실제 확인받은 사실만 사용자 수행으로 적는다. 요약 작성을 위해 새 검증을 자동 실행하지 않으며 실행 정책은 `skills/verify.md`를 따른다.
4. 중요한 내용만 기존 작업 문서에 남긴다. 공식 양식이 없으면 `templates/DECISIONS.md`와 `templates/VERIFY.md`의 필요한 항목을 실제 과제 폴더에서 사용한다. 문서를 에디터로 열어 설명을 읽을 수 있게 경로를 알려준다.

SUMMARY는 현재 구현의 빠른 복습용이다. 한 페이지, 2~3분 안에 훑을 분량을 목표로 하고 목적·핵심 선택·가장 중요한 한계를 앞에 둔다. 150~170분에 AI가 최종 코드와 기록에 맞춰 정리해 경로를 알려주고 핵심 요약을 응답에도 보여준다. 이후 구현이 달라지면 영향받은 문장만 갱신해 알린다. 읽는 시점은 파일 열람이 가능한 제출 확정 전이며 실제 후속 평가 중 AI 답안 작성에는 사용하지 않는다.

## 구현 근거가 있는 구조도

핵심 흐름이 처음 연결됐을 때와 최종 통합 후 실제 코드·설정에 맞는 구조도 하나를 남긴다. 구조가 바뀐 묶음이 끝났을 때 갱신하며, 문구 수정마다 다시 그리거나 문서 갱신만으로 전체 테스트를 반복하지 않는다.

- 상자에는 역할과 실제 기술/제품·대표 파일/함수를 함께 적는다. 프론트 프레임워크, API 서버, 알고리즘 이름/라이브러리와 진입 함수, DB 제품·접근 라이브러리를 확인한다. 의존성에 있다는 이유만으로 실제 사용한다고 쓰지 않는다. 버전이 중요하면 설정/잠금 파일의 선언과 설치·실행에서 확인한 버전을 구분한다.
- 선에는 실제 호출 방식을 적는다. HTTP라면 메서드·경로와 요청/응답의 핵심 필드, 내부 호출이면 함수명, DB 접근이면 ORM/드라이버·주요 테이블/쿼리를 표시한다. 모든 연결을 API라고 부르지 않는다. 읽기/쓰기·반환 방향과 동기/비동기를 필요한 곳에 표시한다.
- 같은 프로세스 안의 모듈과 별도 서버/워커를 구분한다. DB는 제품뿐 아니라 파일/서버/메모리 방식·주요 테이블·재시작 후 유지 여부를 확인한다. DB가 없으면 실제 JSON 파일·메모리 저장 등을 그대로 적는다. 인증정보·개인 데이터는 도식에 넣지 않는다.
- 그림이 복잡하면 상자에는 핵심 이름만 적고 바로 아래 구현 대응표와 호출 표로 상세를 연결한다. 각 연결은 호출하는 코드와 처리하는 코드, DB 모델/쿼리 등으로 뒷받침한다. 코드 확인·실행 확인·미확인·향후 계획을 구분하고 현재 구조에 미구현 서버나 DB를 섞지 않는다.
- 사용자 행동 하나를 골라 화면 파일 → 실제 API/핸들러 → 알고리즘 함수 → 저장/조회 → 화면 응답을 따라 설명한다. 권한 검사 위치, 실패/시간 초과 처리, 구조 선택의 이유와 한계를 함께 짚는다. 없는 단계는 억지로 만들지 않는다.
- 기존 과제 문서에서 Mermaid 미리보기가 되면 사용하고, 지원되지 않으면 외부 연결 없는 SVG 또는 정적 HTML로 보여준다. 미리보기 경로를 알려주고 기존 설명과 연결한다. 도식 때문에 별도 서비스·MCP·디자인 도구를 설치하지 않는다.

## 제출 전 점검

주된 목적에 맞는 설명도 준비한다. 계획형은 ‘어떤 조건을 지키며 무엇을 개선했고 무엇을 포기했는가’, 판단형은 ‘어떤 기준과 근거로 판정했고 무엇이 아직 미확인인가’, 분석형은 ‘어떤 자료와 계산이 결론을 뒷받침하며 어디까지 말할 수 있는가’를 실제 결과로 답한다.

1. AI가 주요 파일 역할과 데이터 흐름을 최종 코드와 대조해 SUMMARY를 완성한다. 사용자는 훑어보고 궁금한 부분이 있을 때만 설명을 요청한다.
2. AI는 주요 결정·검증 결과·미검증·한계를 기록과 맞춘다. 아래는 요약 누락을 확인하는 참고 질문이며, 사용자에게 전부 답하도록 요구하거나 실제 문항을 예측하지 않는다.
   - 구조를 선택한 이유와 포기한 대안은 무엇인가?
   - 입력이 어떤 함수·파일·저장소를 거쳐 결과로 나오는가?
   - 어떤 명령과 조작으로 동작을 확인했는가?
   - 실패하는 입력과 아직 검증하지 못한 상황은 무엇인가?
   - 시스템의 구성요소는 어떤 책임을 가지며 어떤 계약으로 연결되는가?
   - 어떤 DB와 테이블/파일을 실제로 쓰며 어디에 저장되는가? 어떤 호출은 HTTP이고 어떤 호출은 내부 함수/DB 접근인가? 해당 코드 위치는 어디인가?
   - 선택한 안의 이점·단점과 포기한 것은 무엇이며 어떤 조건이면 대안을 택할 것인가?
   - 데이터에 어떤 필드·정답·사례가 없어 무엇을 검증하지 못했는가? 대체 확인으로 어디까지 말할 수 있는가?
   - 환경/시간 제약·설계상 절충·알려진 결함·미검증을 구분할 수 있는가?
   - 병렬 작업은 어떻게 나눴고 최종 결합이 정상임을 어떻게 확인했는가?
   - 시간이 더 있다면 무엇을 먼저 고칠 것인가?
   - AI 제안을 어떻게 채택·수정·거절했고 내가 검증한 부분은 무엇인가?
3. 제출 직전에 구조를 크게 바꾸지 않는다. 사실과 불확실성을 구분하고 제출 확인으로 전환한다.

## 빠르게 읽을 수 있는 설명
- AI는 결론 → 이유 → 구체적인 구현·검증 근거 → 한계 순서로 쉬운 문장을 쓴다. 일반론보다 실제 코드·결정·결과를 담고 대표 파일/함수·API·DB 이름을 짚는다.
- 각 항목은 짧은 본문과 근거 위치로 정리하고 상세 구조도·긴 검사 로그를 중복하지 않는다. 읽기 완료 응답이나 타이핑을 다음 작업의 조건으로 삼지 않는다.
- 질문 전제가 실제 구현과 다르면 그 차이를 먼저 밝힌다. 미구현·미검증을 완료했다고 말하지 않는다.
- 실제 후속 서술형은 AI와 복사·붙여넣기를 사용하지 않는다. 제출된 답안으로 되돌아갈 수 없고, 다음 문항 타이머는 직전 답안 제출 즉시 시작되며 시간이 끝나면 현재 답안이 확정된다.
