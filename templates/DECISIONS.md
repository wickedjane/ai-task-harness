# 설계와 결정 기록

공식 문서가 있으면 필요한 항목만 거기에 통합한다. 실제 과제 작업 폴더에 기록하고 참고용 하네스 원본은 유지한다. 모든 수정 대신 중요한 설계·알고리즘 선택과 변경을 짧게 남긴다.

## 현재 구현의 아키텍처
- 해결하는 문제와 주요 제약:
- 설명 대상 코드 상태/커밋과 실행 환경 (확인 가능한 범위):

여기에 실제 구현의 구조도 하나를 넣는다. 상자에는 역할·실제 기술/제품·대표 파일/함수를, 선에는 HTTP 메서드/경로·내부 함수 호출·DB 접근 방식을 구분해 표시한다. 같은 프로세스와 별도 서버/워커의 경계를 보인다. Mermaid 미리보기가 안 되면 외부 연결 없는 SVG/정적 HTML을 사용하고 여기에 경로를 남긴다.

### 구성요소와 구현 대응

| 구성요소·책임 | 실제 기술/제품·알고리즘 | 구현 파일·함수·설정 근거 | 실행 위치·저장 특성 | 확인 상태 |
|---|---|---|---|---|
| 프론트 | | | 브라우저 등 | 코드 확인 / 실행 확인 / 미확인 |
| API/애플리케이션 | | | 프로세스·실제 포트 등 | |
| 핵심 알고리즘 | 방법·실제로 호출하는 라이브러리 | 진입 함수·주요 처리 파일 | 앱 내부 / 별도 워커 등 | |
| 저장소 | DB 제품과 ORM/드라이버 또는 파일/메모리 | 모델·쿼리·설정 | 주요 테이블·파일/서버·재시작 후 유지 여부 | |

해당하는 행만 쓴다. DB 제품과 접근 라이브러리를 구분하고, 설치만 된 패키지를 실제 사용으로 기록하지 않는다. 비밀번호·토큰·개인 데이터는 적지 않는다.

### 실제 연결과 호출

| 호출자 → 처리자 (파일/함수) | 호출 방식·메서드/경로 또는 함수/쿼리 | 입력 → 출력·읽기/쓰기 | 권한·오류 처리 | 확인 근거 |
|---|---|---|---|---|
| | HTTP / 내부 함수 / ORM·SQL / 파일 / 큐 중 실제 방식 | 핵심 필드·단위·시간대 등 | | 호출 코드·핸들러·모델/쿼리·기존 실행 결과 |

- 사용자 행동 하나의 실제 흐름: 입력/설정 변경 → 위 표의 파일·호출 경로 → 처리·저장 → 응답/표시
- 동기/비동기 처리와 상태/데이터 유지 범위:
- 실패 시 동작·시간 초과 처리와 현재 구조의 한계:

현재 구현·미확인·향후 계획을 구분한다. 실제로 쓰지 않는 서버·DB·배포 구조를 넣지 않는다. 구조가 바뀐 변경 묶음 후와 최종 통합 때 갱신하며, 문서 갱신만으로 전체 테스트를 반복하지 않는다.

|---|---|---|---|
| | | | |

- 선택한 안과 이유 / 선택 주체·사용자 확인 여부:
- 받아들인 단점·제외 범위와 그 영향:
- 적용 파일/함수와 확인 근거:
- 어떤 조건이 바뀌면 다른 안으로 전환할지:

당시에 비교하지 않은 대안은 ‘사후 검토’로 표시한다. AI의 제안을 사용자가 직접 선택했다고 추정하지 않는다.

## 사용자 확인과 AI 제안 검토
| 시점·기능 | AI 제안 | 사용자가 실제 확인·수정한 내용 | 이유 | 결과·근거 |
|---|---|---|---|---|
| | | | | |

사용자가 확인했다고 말한 내용만 직접 확인으로 기록한다. AI가 실행한 검증은 구분한다. 수정 없이 채택한 경우도 확인 근거를 남기며 수정 이력을 만들어내지 않는다.
