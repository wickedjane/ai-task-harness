# 검증과 한계 기록

공식 기록 양식이 있으면 통합한다. 실행 결과와 주장의 근거를 연결하고 AI 실행·사용자 직접 확인·코드만 검토·미실행을 구분한다.

## 현재 변경 묶음과 남은 검증
| 변경 묶음·완료 조건 | 영향 범위·검사·예상 시간 | 사용자 선택·적용 범위 | 담당·실행 시점 | 상태 |
|---|---|---|---|---|
| | 시간 근거가 없으면 미상 | 지금 / 통합 때 / 이번 변경 생략 / 기존 방침 | | 선택 대기 / 실행 대기 / 실행 중 / 완료 / 미실행 |

필요한 묶음만 한 줄로 적는다. 실행 선택·방침·담당 기준은 하네스의 `skills/verify.md`를 따른다.

## 실제 실행
| 대상·파일 상태/버전 | 실행자 | 명령·입력·조작 | 기대 | 실제 결과·출력 위치 |
|---|---|---|---|---|
| | | | | |

이전 근거를 재사용하면 원래 실행 대상·시점/출력과 관련 코드·데이터·설정·의존성·환경이 바뀌지 않았다는 이유를 적는다. 과거 실행을 새 실행으로 표시하지 않는다.

## 요구사항과 예외
| 요구사항·경계 조건 | 확인한 데이터/환경 범위 | 상태 | 근거 |
|---|---|---|---|
| | | 통과 / 실패 / 부분 확인 / 미검증 | |

병렬 작업은 개별 테스트와 최종 통합 테스트의 근거를 구분한다.

## 데이터가 없어 확인하지 못한 것
| 확인하려는 주장 | 부족한 필드·정답·사례·분포 | 수행한 대체 확인 | 여전히 말할 수 없는 것 | 추가로 필요한 데이터·검증 |
|---|---|---|---|---|
| | | | | |

합성 입력으로 분기 동작을 확인해도 실제 데이터 품질·정확도·성능이 검증된 것은 아니다. 정답이 없으면 정확도를 계산했다고 쓰지 않는다. 관측하지 못한 사례를 발생하지 않는 사례로 취급하지 않는다.

## 제약과 한계
| 구분 | 내용과 근거 | 영향받는 사용자·결과 | 현재 대응 | 다음 검증·개선 |
|---|---|---|---|---|
| 환경/시간 제약 · 설계상 절충 · 알려진 결함 · 미검증 | | | | |

발견한 결함과 증거가 부족한 불확실성을 구분한다. 개선은 영향과 우선순위에 따라 정하고 현재 구현처럼 설명하지 않는다.
